2. STEP-BY-STEP PIPELINE EVOLUTION & ACTIONS TAKEN
--------------------------------------------------------------------------------
[PHASE 1: INITIAL BASELINE SYSTEM]
- Actions Taken:
  * Analyzed starting codebase (`dense.py`, `sparse.py`, `hybrid.py`, `benchmark_retrieval.py`).
  * Dense & Sparse retrievers were fetching only top 5-10 items.
  * Measured Precision@5 (80%) and Recall@5 (39.2%).
  * Issue identified: Low Recall@5 meant critical clinical facts were omitted.

[PHASE 2: METRIC SUITE EXPANSION & TEXT CLEANING]
- Actions Taken:
  * Updated `sparse.py`: Added regex tokenization (`re.findall`) and English `STOP_WORDS`
    filtering ("and", "causes", "with", "causing") so PostgreSQL full-text search does not match common words.
  * Updated `benchmark_retrieval.py`: Expanded evaluation metrics to calculate Precision@5,
    Recall@5, Recall@10, Recall@20, MRR, NDCG@5, Latency, and Overlap.

[PHASE 3: TWO-TIER RETRIEVAL & RRF CANDIDATE POOL EXPANSION]
- Actions Taken:
  * Updated `dense.py` and `sparse.py`: Changed default candidate retrieval size `top_k` to 30.
  * Updated `hybrid.py`: Modified `reciprocal_rank_fusion` to deduplicate using database primary key `id`.
  * Expanded `hybrid_search` to fetch 30 candidates per retriever before applying RRF:
    RRF_score(d) = sum( 1 / (60 + rank(d)) ).
  * Final output size maintained at top 5 for LLM context generation.
- Results:
  * Recall@20 surged from 40.4% -> 60.4% (+20.0%).
  * Latency dropped from ~1099ms -> ~325ms due to clean thread parallelization.

[PHASE 4: CANDIDATE POOL SIZE EXPERIMENTS]
